# 短剧 SaaS 海外部署、容量与安全方案

## 1. 目标和边界

本方案面向 20～30 个商家，业务初期用户较少，但平台需要平滑扩容到峰值 10,000 人同时在线观看。首期部署在海外，目标市场可能包含日本、美国等地区，暂不锁定单一首发国家。

核心原则：

- 视频流量全部由对象存储和 CDN 承载，应用服务器不转发视频文件。
- 应用、数据库先单区域部署，CDN 从第一天起全球分发；有真实流量和延迟数据后再决定第二应用区域。
- 商家共享一套 SaaS 服务，但数据、域名、配置、账务、文件路径和日志必须按 `tenant_id` 严格隔离。
- 初期控制固定成本，扩容依靠无状态应用、多级缓存、队列和 CDN，而不是提前建设复杂的多地域系统。
- 本文容量值是初始基线，正式放量前必须用真实接口和视频码率做压测校准。

## 2. 关键容量换算

“10,000 人同时在线”主要是视频分发容量，不等于应用服务器需要维持 10,000 路视频连接。

按平均视频码率估算：

| 平均码率 | CDN 边缘峰值带宽 | 连续峰值 1 小时的下行流量 |
| --- | ---: | ---: |
| 1.0 Mbps | 10 Gbps | 约 4.5 TB |
| 1.5 Mbps | 15 Gbps | 约 6.75 TB |
| 2.0 Mbps | 20 Gbps | 约 9 TB |

流量公式：

```text
视频流量 GB = 观看分钟数 × 平均码率 Mbps × 60 ÷ 8 ÷ 1000
CDN 费用 = 视频流量 GB × 对应国家/地区的每 GB 单价
```

因此 CDN 必须提前确认可提供至少 20 Gbps 的峰值能力，并额外保留约 50% 突发余量，同时解除账户默认流量或带宽限制。实际费用主要由观看分钟数、码率、用户所在国家和 CDN 合同决定，通常远高于应用服务器的固定费用。

首期不做自动转码，当前上传接口接受受控 MIME 的 MP4/WebM/QuickTime 原文件并依赖对象存储 Range 请求。运营侧应优先要求 H.264 + AAC MP4，并在上传前生成独立试看文件；当前系统没有伪装成已经具备 HLS、多清晰度或自动转码。建议后续把转码和可信媒体探测作为独立队列任务接入。

## 3. 分阶段部署架构

### 3.1 开发和内测阶段

用于产品开发和少量邀请测试，不承诺高可用：

- 1 台 4 vCPU / 8 GB 应用主机，使用容器运行 API、管理后台、H5 和异步任务。
- 托管数据库，建议 2 vCPU / 4～8 GB、100 GB SSD 起步；不要把正式数据库放在应用主机内。
- 托管 Redis 1～2 GB；预算极低时测试环境可同机运行，正式环境不可同机。
- 对象存储、CDN、DNS/WAF 从内测开始启用，避免上线前更换视频 URL 体系。
- 单独的测试域名、测试支付账户和测试对象存储桶，禁止与生产共用密钥。

### 3.2 初期正式运营阶段

在付费用户开放后使用，固定成本仍保持较低：

- CDN/WAF 前置，应用只允许负载均衡器或可信边缘节点访问。
- 2 台无状态应用实例，每台建议 2～4 vCPU / 4～8 GB；跨同一区域的两个可用区部署。
- 1 个托管关系型数据库主实例，建议 4 vCPU / 8～16 GB、100～200 GB SSD，开启高可用、自动备份和时间点恢复。
- 1 个托管 Redis，建议 2～4 GB，启用持久化和自动故障转移；用于会话、验证码、限流、热点缓存和短期状态。
- 初期异步队列可以使用云托管队列，或使用独立 Redis 逻辑实例/集群承载；不要和会话缓存混用同一淘汰策略。
- 至少 2 个队列 Worker，处理邮件、短信、推送、导入、导出、统计和支付回调后的异步任务。
- 静态管理后台和 H5 优先直接托管在对象存储/CDN，不占应用计算资源。
- 日志、指标、错误追踪和告警接入托管服务，避免自行维护监控集群。

### 3.3 扩容到峰值 10,000 人在线

视频仍由 CDN 承载，业务系统按实际 API 请求率横向扩容：

- CDN 目标缓存命中率不低于 95%，启用分层缓存/Origin Shield，回源只访问对象存储的私有源站域名。
- 应用建议以 4 vCPU / 8 GB 为一个扩容单元，从 4～8 个实例开始压测；按 CPU、P95 延迟和请求率自动扩缩。
- 负载均衡层至少支持 2,000～5,000 API RPS 的扩展空间，应用会话全部放 Redis 或使用无状态短令牌。
- 数据库建议 8～16 vCPU / 32～64 GB 起步压测，增加只读副本承担报表、搜索和非实时统计；写入仍走单主库。
- Redis 扩容到 8～16 GB 或分片集群，缓存、会话、限流、排行榜和消息通道使用不同 Key 前缀及资源配额。
- 队列改为专用托管消息队列，按任务类型拆分队列和 Worker 池；支付、通知、导入、统计互不阻塞。
- 弹幕/在线消息使用独立 WebSocket 网关，2～4 个无状态实例起步，通过 Redis Pub/Sub 或托管消息服务广播；禁止依靠单机内存保存连接状态。
- 报表使用异步汇总表，不允许商家后台直接对订单、播放明细等大表执行全表统计。
- 搜索量不大时继续使用数据库索引；只有模糊搜索、分词和数据量达到瓶颈后再增加搜索集群。

正式扩容值须通过压测确定。建议至少验证 1,500 API RPS、10,000 个 WebSocket 连接、支付回调突发、批量推送、批量导入和数据库故障切换。视频峰值用 CDN 压测或供应商容量确认完成，不要用应用服务器模拟转发视频。

## 4. CDN、对象存储与播放安全

### 4.1 选型要求

可选择同一云厂商的对象存储 + CDN，也可选择低出网成本的对象存储配合全球 CDN。正式选择前对日本、美国及其他重点区域分别比较：

- 视频下行单价、分区价格和 95 峰值计费方式。
- 对象存储到 CDN 的回源费用，以及是否提供免费/低价回源。
- 20 Gbps 以上突发能力、账户默认限额和 DDoS 处理能力。
- HLS、Range 请求、Origin Shield、签名 URL/Cookie 和边缘鉴权能力。
- 自定义域名证书数量、API 自动化、日志实时性和按商家统计能力。
- 对象存储数据驻留区域及服务条款是否覆盖目标国家。

对象存储源站必须私有，禁止公开列目录和使用永久公开 URL。上传、播放均使用短期签名；CDN 回源使用专用身份或仅允许 CDN 回源地址。

### 4.2 文件与缓存规则

- 路径至少包含 `tenant_id/content_id/version`，严禁不同商家复用可猜测的文件地址。
- 视频分片和带版本号的静态资源使用长缓存；播放清单、授权信息、首页配置使用短缓存并支持主动刷新。
- 播放签名放在 CDN 不参与缓存键计算的字段中，或使用签名 Cookie；否则每个用户的签名 URL 都会形成独立缓存，命中率无法达到目标。
- 替换视频时生成新版本路径，不原地覆盖旧文件，避免 CDN 脏缓存。
- 播放权限实时绑定商家、用户、内容和权益；当前对象存储签名 URL 有效期限制为 2～5 分钟且不支持离线，播放器需在长视频播放期间安全续签。
- 启用防盗链、异常流量检测、单账号并发限制和 IP/设备频率限制；Referer 只能作为辅助，不能替代签名鉴权。
- CDN 日志按商家归集播放字节数、命中率、状态码和热门内容，为成本分摊与盗刷检测提供依据。
- 无引用文件进入回收站或低频层，经过保留期后再清除；删除操作必须可审计。

### 4.3 供应商策略

初期使用一个主 CDN，减少域名、证书和缓存刷新复杂度。达到以下任一条件后再接入第二 CDN：单月视频费用达到可谈判规模、单一供应商在重点地区质量不稳定、需要容灾，或存在单一供应商容量限制。

第二 CDN 通过 DNS/流量调度切换，播放 URL 保持业务域名不变。切换前必须验证签名算法、缓存键和日志字段一致。

## 5. 数据库、Redis 与队列

### 5.1 关系型数据库

采用 PostgreSQL 16 托管数据库（代码最低兼容 PostgreSQL 14）。要求：

- 所有商家业务表强制包含 `tenant_id`，常用索引把 `tenant_id` 放在前部。
- 唯一约束必须包含租户维度，例如 `(tenant_id, email)`，避免跨商家误判冲突。
- 订单、支付流水、余额、提现和佣金使用数据库事务、唯一业务号和幂等键。
- 读写连接池设上限，实例扩容时不能让总连接数随应用实例无限增长；必要时使用托管数据库代理。
- 慢查询阈值、执行计划和大表增长按周检查；播放明细、审计日志和消息记录按月或时间分区。
- 商家数据导出走只读副本和异步任务，导出文件使用短期下载链接。
- 生产环境禁止手工直连修改账务；紧急变更需工单、双人复核和审计记录。

20～30 个商家不需要每商家单独数据库。共享库 + 强制租户隔离更适合当前规模；若未来出现监管或大型独立客户，再把指定商家迁移到独立数据库。

### 5.2 Redis

Redis 只保存可重建数据或短期状态，不作为订单、余额等事实数据的唯一存储。建议按用途隔离：

- 会话与设备登录：不使用随机淘汰，保持明确 TTL。
- 验证码和登录限流：短 TTL、按 IP/账号/设备组合限流。
- 业务缓存：允许 LRU 淘汰，Key 必须包含商家维度。
- 排行榜和在线状态：允许异步回写或重建。
- Pub/Sub：只传实时事件，不保证消息持久化；需要可靠消费的任务进入队列。

### 5.3 队列

所有外部服务和长任务异步化：短信、邮件、App 推送、支付后通知、内容导入、Excel 导出、数据汇总、CDN 刷新及以后接入的转码任务。

队列消息必须包含 `tenant_id`、任务类型、业务幂等键、重试次数和追踪 ID。支付类任务与营销群发分开队列；采用指数退避、最大重试次数和死信队列，死信进入告警和人工处理流程。

## 6. 域名与证书

建议域名层次：

- 平台 API：`api.example.com`
- 总后台：`admin.example.com`
- 商家后台：`console.example.com`
- 平台分配的商家 H5：`{tenant}.app.example.com`
- 商家独立绑定域名：商家将 CNAME 指向平台提供的边缘域名

平台分配域名使用 `*.app.example.com` 通配符证书。商家自定义域名在绑定前必须完成 DNS TXT/CNAME 所有权验证，并自动申请、续期和吊销证书。必须处理以下状态：验证中、生效、续期失败、解绑、商家过期和域名被其他商家占用。

所有域名只解析到 CDN/WAF 或负载均衡器，不暴露应用和对象存储源站 IP。启用 TLS 1.2+、HSTS、自动续期告警；支付回调域名独立配置健康检查，避免前端域名变更影响收款。

商家过期时，后台进入只读，H5 显示平台可配置的暂停页；不要立即释放自定义域名。经过保留期并确认解绑后再允许其他商家绑定，防止域名接管。

## 7. 多地区策略

初期只选择一个海外主区域。日本、美国均可能成为市场时，可以先选东京作为默认候选，也可以根据云厂商价格和团队运维条件选择美国西部；最终用内测阶段的真实用户延迟和 CDN 日志决定。

第一阶段：

- 应用、主数据库、Redis 和队列位于同一主区域，减少延迟和跨区费用。
- 视频和静态资源由全球 CDN 覆盖，日本、美国使用当地边缘节点。
- 数据库备份每日复制到另一个海外区域或另一个账户。

不要在用户量很少时做跨地区双写数据库。它会显著增加账务一致性、故障判断和成本。达到以下条件后再建设第二应用区域：主区域故障造成的业务损失不可接受、某地区 API P95 延迟长期超过目标、监管要求数据驻留，或单区域资源不足。

第二地区初期采用冷备或温备：预先准备基础设施模板、镜像、密钥恢复流程和只读备份，故障时通过 DNS 切换。只有明确需要 RTO 小于 30 分钟时，才建设持续运行的热备应用和跨区数据库复制。

## 8. 备份与灾难恢复

初期正式环境目标：RPO 不超过 15 分钟，RTO 不超过 4 小时。业务增长后目标：RPO 不超过 5 分钟，RTO 1～2 小时。

- 数据库开启连续日志/时间点恢复，初期保留 14 天，增长后保留 30 天。
- 每日完整快照保留 30 天，每周快照复制到另一地区或独立备份账户并保留 90 天。
- 对象存储开启版本控制；误覆盖/误删除保留 30 天，随后按生命周期进入低频层或清除。
- 配置、基础设施代码、数据库结构和部署镜像进入版本库/镜像仓库；密钥只在密钥管理服务保存，不进入源码或备份文档。
- 每月抽样恢复数据库和对象，至少每季度进行一次完整灾备演练并记录真实 RPO/RTO。
- 账务表恢复后必须进行订单、支付流水、余额和提现的对账，不能只以数据库启动成功作为恢复完成。
- 备份使用独立权限，生产应用账号不得拥有删除历史备份的权限。

## 9. 监控、日志与告警

### 9.1 必监控指标

- API：请求率、P50/P95/P99 延迟、4xx/5xx、登录/播放授权/下单成功率。
- 应用：CPU、内存、实例数、连接池、进程重启、依赖服务超时。
- 数据库：CPU、磁盘空间、IOPS、连接数、锁等待、慢查询、复制延迟。
- Redis：内存、命中率、淘汰数、连接数、热点 Key、主从切换。
- 队列：积压数、最老消息等待时间、重试和死信数。
- CDN/存储：带宽、流量、缓存命中率、回源流量、403/404/5xx、热点 URL、每商家用量。
- 业务：在线设备、播放启动失败率、支付回调延迟、提现待审、推送失败和商家成本异常。

### 9.2 日志与告警

日志统一使用结构化格式，至少包含时间、环境、服务、追踪 ID、`tenant_id`、用户/管理员 ID 和结果码。密码、验证码、令牌、支付密钥、完整手机号/邮箱不得写日志。

应用日志热存储 7～14 天，压缩归档 30～90 天；支付、提现、权限和后台操作审计根据业务要求保留更久。高优先级告警包括全站不可用、支付回调失败、数据库故障、队列严重积压、证书临期、备份失败、CDN 流量突增和疑似跨租户访问。

配置从外部网络执行的合成监控，持续检查 H5 打开、登录、播放授权、下单测试链路和管理后台。告警必须有负责人、升级规则和处理手册，避免只有监控面板无人响应。

## 10. 安全基线

- 公网仅开放 CDN/WAF 和负载均衡器；应用、数据库、Redis、队列和对象存储源站位于私网。
- 总后台强制 MFA，支持高风险操作二次验证；权限按最小授权拆分，提现、退款、支付配置和密钥查看必须审计。
- WAF 启用常见攻击规则、Bot 管理和分级限流；登录、注册、验证码、播放签名、评论、弹幕和导出分别配置限流。
- 商家域名、请求令牌、数据库查询、缓存 Key、文件路径和队列消息都必须校验租户归属，不能只依赖前端传入的 `tenant_id`。
- 密钥放入托管密钥/Secret 服务，定期轮换；不同环境、不同商家支付通道使用独立密钥。
- 上传文件验证 MIME、扩展名、文件头和大小，必要时病毒扫描；上传凭证只能写入指定商家路径。
- 支付回调验证签名、金额、币种、商家和订单状态，并用唯一键保证幂等；不自行保存银行卡数据。
- “万能验证码 8888”是临时联调能力，不具备账号白名单：只有同时设置 `CUSTOMER_UNIVERSAL_OTP_ENABLED=true` 和生产不安全确认开关时才生效，命中会审计。正式开放前必须恢复两个开关为 false，不能把它当生产登录方式。
- 依赖包、容器镜像和代码持续做漏洞扫描；高危漏洞修复后才能发布生产。
- 每次发布使用滚动或蓝绿部署，保留上一稳定镜像；数据库迁移遵循先兼容扩展、后清理旧字段，确保可回滚。

## 11. 成本控制

固定成本与视频成本分开管理：

1. 固定平台成本：应用实例、负载均衡、数据库、Redis、队列、日志和监控。
2. 用量成本：CDN 下行、对象存储、回源、短信、邮件、推送和第三方支付。

控制措施：

- 初期单区域部署，计算实例按 2 台生产最小规模运行；通过自动扩缩容应对活动峰值。
- 优先使用托管数据库、Redis、队列和监控，减少运维人力；不提前建设 Kubernetes、搜索集群或跨区双活。
- 视频采用合理码率和长缓存，启用 Origin Shield；这是降低成本最有效的手段。
- 每个商家记录 CDN 字节数、存储量、短信/邮件数和推送数，即使暂时不收费也要保留成本账本。
- 设置平台总预算、单商家日预算和异常倍数告警。流量突然放大时先限速/冻结异常令牌，不直接关闭全站。
- CDN 合同按日本、美国等区域分别核算；月流量稳定后再谈阶梯价或多 CDN 竞价。
- 日志设置采样和生命周期，视频访问日志进入低成本存储，不长期留在昂贵检索层。
- 对数据库、Redis、对象存储和 CDN 每月做容量复盘，按 30 天增长趋势扩容，避免按想象一次性购买大规格。

不建议在未确定真实观看时长和码率前给出固定月费承诺。预算模型至少输入：各地区观看分钟数、平均码率、CDN 单价、缓存命中率、对象存储容量、回源单价及短信/邮件数量。

## 12. 上线门槛与扩容触发条件

初期生产上线前必须完成：

- 数据库备份和一次实际恢复演练。
- CDN 私有回源、播放签名、防盗链和流量告警。
- 商家域名所有权验证、证书自动续期和解绑保护。
- 租户隔离自动化测试，覆盖查询、导出、缓存、文件和队列。
- 登录/验证码限流、总后台 MFA、支付回调签名与幂等。
- 监控、告警、审计日志、发布回滚和生产密钥隔离。

满足以下任一条件时进入扩容评估：

- API P95 连续 15 分钟超过 300 ms，或应用 CPU 连续超过 65%。
- 数据库 CPU 连续超过 60%、连接超过 70%，或慢查询影响核心链路。
- Redis 内存超过 70%、出现淘汰或队列等待时间超过业务目标。
- CDN 缓存命中低于 95%、回源带宽异常，或峰值带宽达到供应商限额的 60%。
- 单商家占平台资源超过 30%，需要独立限流、Worker 或数据库资源。
- 备份恢复时间无法满足既定 RTO。

扩容顺序优先为：修正缓存和慢查询 → 增加应用/Worker → 提升数据库规格和增加只读副本 → 拆分 Redis/队列 → 增加第二地区。视频容量优先通过 CDN 配额、缓存和合同扩展处理，不扩应用服务器带宽。
